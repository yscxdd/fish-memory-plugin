## R1（P0）`memory rechain` 与宿主写档案不互斥：丢消息，而且修完链又断

### 复现

```js
// 1) 造 20000 行「链断了」的档案（prev 全错）
// 2) 子进程每 5ms 追加一条合法记录（模拟你正在聊天）
// 3) 主进程跑 rechain(dir)
```

实测输出：

```
rechain 用时 105ms，changed=1(1 文件)
文件从 20000 行 → 20184 行；其中并发写的 184 条还在
子进程写了 200 条，实际保住 184 条
```

然后：

```
$ memory verify --dir D:/tmp/fm-rc2
  档案 1 个文件 · 链有问题
  ✗ 2026-11-08.jsonl: hash 对不上
```

**16 条消息没了，而且修完的库比修之前更糟（新断了一处）。**

### 根因

`lib/rechain.js:40` 把整个文件读进内存 → `:65` `atomicWriteText(file, text)`（tmp + rename 整文件替换）。
这中间没有任何锁；而写入方 `lib/archive.js` 的 `_append` 是**按天文件加锁**的（`withDayLock`），两边不是同一套互斥。

- 读与替换之间落进来的行 → 被旧的整份快照覆盖 → 丢；
- 子进程缓存的 `prev` 是旧 hash，而 rechain 把前面的 hash 全重算了 → 它接上去的那条 `prev` 对不上 → 链再断；
- 丢掉的那些行，游标（`20_state/cursors/<session>.json`）早就前移了，**不会重放**——永久丢失。

### 为什么这一点比"链断了"严重得多

v0.78 加 `rechain` 的初衷是"链断了能修"。但现在的形态是：**修链的工具本身会吃消息**。而它恰恰是最需要的时候会被用（库已经出问题、人着急的时候）。

### 修法（改 20 行以内）

1. `lib/archive.js` 把 `withDayLock` 导出（或加一个 `withArchiveLock(dir, file, fn)`）；
2. `rechainFile()` 内部改成：**加锁 → 锁内重新读文件 → 重算 → 写**；
3. 再加一道"写前复核"：rename 之前 `statSync(file).size` 必须和读进来时一致，不一致就放弃并报"有人正在写，稍后再跑"（宁愿不修，不能多吃）；
4. `scripts/memory.mjs:722` `cmdRechain` 加护栏：目录里存在 `10_archive/messages/*.lock` 或 `20_state/.lock` 时**默认拒绝**，要 `--force` 才继续。

### 验收

`test/archive-race.test.js` 加一条：

- 造 5000 行断链档案，起一个子进程持续 append；
- 跑 `rechain`；
- 断言：① 追加的条数一条不少；② `checkArchive(dir).ok === true`；
- 反面用例：锁存在时 `cmdRechain` 不带 `--force` 必须退出码非 0。

## R2（P1）MCP 的四条路，只修好了"点"，没修"档案"

v0.78.0 把 `memory_search / get / evidence` 的点检索都过了 `visibleIn()`——这部分**确实修好了**（我复核过：`scope: group:*` 的点不会回给 `dm:master`）。

但**档案那一半没修**。实测（造一个只有私聊档案的库）：

```
$ memory_search {"query":"银行卡尾号","scope":"group:123456"}
记忆点 0 条（scope=group:123456）

档案原话：
- 2026-11-01T10:00 · 你：私聊里说的：我的银行卡尾号是 8899，别告诉别人

$ memory_get {"id":"seq:1","scope":"group:123456"}
seq:1 · 你：私聊里说的：我的银行卡尾号是 8899，别告诉别人
```

### 根因

| 位置 | 问题 |
|---|---|
| `scripts/mcp.mjs:209` | `searchArchive(dir, q, { limit: 5 })` —— **没有任何 scope 参数** |
| `lib/recall.js:19` | `searchArchive` 只做 `indexOf`，不过作用域（它对 `scope` 一无所知） |
| `scripts/mcp.mjs:298` | `readPointArchive()` 返回 `readArchive(dir).messages` **全量**，`memory_get seq:` 直接在里面找 |

好消息：档案记录**已经带 `scope` 字段了**（`lib/archive.js:129`，v0.78.0 补的），所以修法是三行过滤，不用迁移。

### 修法

```js
// recall.js
export function searchArchive(dir, query, { limit = 5, window = 60, scope = null } = {}) {
  ...
  for (const m of messages) {
    if (scope && (m.scope || 'dm:master') !== scope && (m.scope || 'dm:master') !== 'global') continue
    ...
```

`mcp.mjs` 里 `searchArchive(..., { scope })`、`memory_get seq:` 的 `filter((m) => (m.scope || 'dm:master') === scope || m.scope === 'global')`。

### 验收

`test/audit-v078.test.js` 现在有 scope 用例，但只覆盖点。补：**档案里放一条 `scope: dm:master` 的消息，`memory_search/get` 带 `group:` 时必须一条都不返回**（这条测试写完，本项才算关）。

## R3（P1）按天写锁是对的，但"释放 = 删除文件"在你机器上贵了 100 倍

### 逐条实测（同一条消息、同一台机器、同一个 Node）

| 版本 | 每条写入耗时（20 条平均） |
|---|---|
| v0.77.0 | **12 ms** |
| v0.78.1 | **125 ms** |

归因确认：把 `withDayLock` 那行换成直接调用（`fm0781-nolock` 副本），耗时回到 **15 ms**。
所以多出来的 ~110ms 全在锁上。

### 为什么是它：这台机器"删文件"特别慢

```
写 30 个新文件        16 ms
删 30 个文件        7316 ms   ← 244ms/次
写 + 改名 30 次       38 ms   ← 改名便宜
同名 wx+unlink 30 次 6904 ms
```

C 盘（`11127ms`）、D 盘、**真库所在目录（`9129ms`）** 三处一致。所以不是 NTFS 某处的问题，是这台机器上有东西在拦"删除"（杀毒/EDR 的实时防护最常见）。**而这不是插件的错，但插件踩在了上面。**

`lib/archive.js:280` 的 `unlinkSync(lock)` 就是那一下。

### 顺带的后果

`withDayLock` 用 `Atomics.wait` 忙等（`lib/archive.js:204` `sleepMs`），是**同步阻塞**：
- 单窗口：每条消息让宿主事件循环停 ~110ms（2 条/轮 ≈ 220ms/轮）；
- 两窗口 + 抢锁：最多 2s 一次，期间宿主什么都干不了。5 进程 × 60 条实测总耗时 **70.5s**。

### 修法（两档，先做 A 就够）

**A. 释放改用改名，删除挪到退出时批量做**（实测 30 次 51ms，1.7ms/次）：

```js
// 释放
try { renameSync(lock, `${lock}.${process.pid}.free`) } catch { /* ignore */ }
// 启动/退出时清一次：readdir 里 *.lock.*.free 一律 rm
```

**B. 只在真争用时才加锁**：现在 `_append` 里已经算了 `_sizes`（`lib/archive.js:359`）。若 `sizeNow === expected`（说明自上次写之后没人动过这个文件），可以直接追加、跳过加锁；只有对不上（或首次写）时才走 `withDayLock`。这把"单窗口日常聊天"的锁成本降到 0，只在"真的两个窗口"时才付。

**C. 顺带**：`sleepMs` 的 5ms 忙等改成 `node:timers/promises` 的 `setTimeout`——但 `_append` 是同步函数，改动大；建议只做 A+B。

### 验收

`test/archive-race.test.js` 加一条性能护栏（别用绝对时间，用相对）：同一份 300 条，`withDayLock` 版本耗时 ≤ 无锁版本 × 2。以及：连写 300 条后 `50_log/archive-race.log` 里不应出现任何 `lock-timeout`（当前 5 进程实测 294 行）。

## R5（P2）`hash` 不覆盖 `scope` / `mode`：改归属不掉链

`lib/archive.js:147` `hashOf` 只算六项：`seq / session / role / ts / msgid_plat / text`。

实测（把库里第 2 条改一改，再跑 `verifyChain`）：

```
只改 scope → {"ok":true,"count":3}
只改 mode  → {"ok":true,"count":3}
只改 role  → {"ok":false,"at":1,"reason":"hash 对不上"}
```

也就是说：**把一条私聊消息的 `scope` 改成 `group:999`，验链是绿的**——而 `scope` 正是隔离的边界字段，`mode` 正是"任务窗只读"的闸门字段。你花了两个版本建立的"改任何东西都有账"，恰好漏掉了最需要防伪造的两个字段。

### 修法

`hashOf` 加 `scope`、`mode`，但**不能直接加**——加了以后所有旧记录 `hash` 全对不上，`verify` 一片红。

按版本走：

```js
export function hashOf(rec, v = rec.hash_v || 1) {
  const base = [rec.seq, rec.session, rec.role, rec.ts, rec.msgid_plat, rec.text]
  if (v >= 2) base.push(rec.scope || 'dm:master', rec.mode || '')
  return sha8(base.join('\u0000'))
}
```

新记录写 `hash_v: 2`；`verifyChain` 按 `r.hash_v || 1` 算。旧档案不动，新档案才受保护。

### 验收

`test/archive.test.js`：v2 记录改 `scope` → `verifyChain` 必须报 `hash 对不上`；v1 老记录改 `scope` → 仍 `ok`（不追溯，别把老库弄红）。

## R7（P3）清单指纹只挡 `tools/call`，不挡 `tools/list`

`scripts/mcp.mjs:325`：`tools/call` 走 `callTool()` → 先查 `manifestMismatch()`；而 `tools/list`（`:324`）**无条件返回当前清单**。

后果：客户端看到的清单已经是新的，只是调用会被拒。既然注释里写的是"清单变过就该由人确认"，`tools/list` 也应该在指纹不符时**只返回一个 `fish-memory-manifest-changed` 说明工具**（或者空清单 + error），否则"确认"这一步永远等不到。
