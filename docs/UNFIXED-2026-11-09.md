## R5（P2）`hash` 不覆盖 `scope` / `mode`

### 现状

`lib/archive.js`：

```js
export function hashOf(rec) {
  return sha8([rec.seq, rec.session, rec.role, rec.ts, rec.msgid_plat, rec.text].join('\u0000'))
}
```

六项里没有 `scope`、没有 `mode`。所以把一条私聊记录改成 `scope: group:999999`，`memory verify` 依旧是绿的。

### 为什么这是问题

链的作用是"**能发现非蓄意的改动**"——它发现不了蓄意改写（32 位裸 hash、无签名、锚还在同一个库里；能改文件的人也能用 `rechain` 把整条链重算一遍）。而 `scope` 恰恰是**决定谁能看到它**的字段——
今天改它能瞒过验链，等于"隐私归属"这一项不在防篡改范围内。接群之后这条会变得更重要。

### 复现

```powershell
node -e "const {readFileSync,writeFileSync}=require('node:fs');const f='fish-memory/10_archive/messages/2026-11-08.jsonl';const rows=readFileSync(f,'utf8').trim().split('\n').map(JSON.parse);rows[1].scope='group:999999';writeFileSync(f,rows.map(r=>JSON.stringify(r)).join('\n')+'\n')"
node scripts/memory.mjs verify --dir fish-memory     # 仍然「链完整」
```

### 为什么不修（这次）

**没有版本标记的话，改 `hashOf` 是一次性把历史全弄红。**

已入库的记录是用 v1 口径算的 hash；新口径一上线，`verify` 会认为**每一条历史记录都被篡改过**。
那不是"发现了一个问题"，那是"制造了一个更大的问题"——和今天 `rechain` 吃消息是同一类错误：
**修复工具把现场毁了。**

正确做法（下个版本单独做）：

1. 记录加 `hash_v: 2`；
2. `hashOf(rec, version)`：v1 = 六项，v2 = 六项 + `scope` + `mode`；
3. 验链时按每条自己的 `hash_v` 选口径（老记录缺字段 → 按 v1 验，不许报错）；
4. 新写入一律 v2；
5. `rechain --upgrade-hash` 才把老记录迁到 v2（**只在新版本上做一次，且要备份**）。

**代价**：一次性改动 `hashOf` 签名 + 3 处调用 + 验链分支 + 迁移命令，约半天。

### 什么时候必须修

**接群之前。** 在那之前，`scope` 只有 `dm:master` 一个值，改了也看不出差别。

## N2（P3）CSP 的 `script-src 'unsafe-inline'`

### 现状

`scripts/serve.mjs`：

```text
default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline';
connect-src 'self'; img-src 'self' data:; ...
```

`script-src 'unsafe-inline'` 的意思是：**页面里任何一段 inline `<script>` 都能跑**。
所以"加 CSP"挡得住外部脚本、挡不住"有人往页面里塞一段脚本"。

### 为什么现在风险低

dashboard 的数据全部走 `textContent`（`scripts/dashboard-html.mjs:68`），
`innerHTML` 只用来清空（`el.innerHTML = ''`）。**没有把记忆数据拼进 HTML 的地方**——
这正是 `secure_scan` 那条 "HTML 写入点" 告警被判定为假阳性的原因。

### 为什么不修（这次）

要真正去掉 `unsafe-inline`，得把 `<script>` 搬到 `/dashboard.js` 端点，再加 `script-src 'self'`。
改动面是"服务端多一条路由 + 页面拆文件 + 引用路径"，而收益是**防一个还不存在的注入点**。

### 但它值得一句注释（已加）

`serve.mjs` 那段已经写明：CSP 是纵深防御，**真正的防线是 `textContent`，改页面时别把数据插进 script**。

### 什么时候必须修

**如果哪天 dashboard 要显示"用户可控的链接或 HTML"**（比如把记忆点渲染成 markdown），
那时 `textContent` 的假设就不成立了，必须先把 script 拆出去。

## N3（P3）零宽空格会跟着数据走

### 现状

`neutralizeHeadings` 把行首 `#` 变成 `\u200b#`。这是**出口净化**，只在"要进模型上下文"时做，
磁盘上的原文不动。但：

- 如果哪天有人把**净化后的文本**导出（备份、复制粘贴、dashboard 展示），零宽字符跟着走；
- 之后的搜索里 `# SYSTEM` 匹配不到那个加了零宽字符的字符串。

### 为什么不修（这次）

它只影响"看起来像标题"的字符串（记忆点正文里出现行首 `#` 的情况本身罕见），
而且**不影响档案原文**。修它要么改净化策略（比如换成"标题降级为普通文字"而不是插零宽），
要么在导出时统一清洗——两者都比现在复杂。

### 替代方案（已做）

在 `memory fields` 的注释里说明这件事，比改动代码更划算：

> 记忆点正文里的行首标题会在**注入时**被插入零宽字符；磁盘原文不变，导出的净化文本带不可见字符。

**如果以后做"导出记忆库为 markdown"**，那一步要先剥掉 `\u200b`。
