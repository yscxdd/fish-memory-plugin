# 让一个聊天角色"记得住、会忘、还记得自己怎么变的"：一份可复用的实现参考

写于 2026-11-03。这份是给别人看的：讲**思路**、**参数**、**坑**，不涉及任何具体的人或对话。

如果你要做的是一个**跨越很多天、记得住事、会忘、人格会缓慢漂移**的角色——不是一个把上一轮对话塞进上下文的机器人——这份文档就是为你写的。

---

## 0. 先看这一节，决定要不要往下读

### 这份文档在讲什么

一个真正跑起来的记忆 + 人格插件，被拆成七个可以独立实现的部分：

```
记忆   记得发生过什么，且来源可追
遗忘   忘得掉：先隔离、能被唤醒、最后真的消失
惦记   她放不下什么，什么时候释怀
人格   她是谁，怎么允许自己变
口音   她怎么说话，且不许人替她写
隐私   库里的凭据不该存在
账本   一天花多少钱，钱花在哪
```

每节都是：**为什么这么想 → 具体怎么做 → 参数怎么定 → 怎么验收 → 哪里会翻车**。

### 不适合谁

- 想要"一句话设定就完事"的：这套要写代码、要跑几百个测试、要调参数。
- 想要"人格完全自由发挥"的：核心是**约束**——锁定的不许动，动一次要过六道闸。
- 想要"立竿见影"的：它的价值在第三个月才显出来，前两周你会觉得"这不就是存文件吗"。

### 一个前置判断

**长提示词解决不了连续性问题。** 提示词是"这一轮"的，连续性需要"跨轮的状态"。
状态必须落盘，且必须有人负责读、负责写、负责裁剪、负责遗忘、负责证明没被篡改。

这就是整份文档的主线：**把"她是谁"从提示词里搬进磁盘。**

## 1. 总体架构与职责边界

```
宿主（DeepSeek Harness 之类）
 └ 插件（本文全部内容）
    ├ lib/host.js    ← 唯一碰宿主 API 的文件（8 个面：effect/on/get/interval/logger/skills/tools/systemPrompt）
    ├ lib/*.js       ← 纯函数：记忆、遗忘、人格、口音、统计
    └ scripts/       ← 离线 CLI：verify / audit / stats / gold / selfcheck
       └ 模型（云端）
```

### 关键边界

| 谁 | 负责 | 不负责 |
|---|---|---|
| 宿主 | 消息收发、事件、会话、上下文拼装 | 记忆、遗忘、人格 |
| 插件 | **所有状态**：记忆、遗忘层、缺口、人格、口音、脱敏 | 渲染回复 |
| 模型 | 这一句话怎么说 | 记得什么、她是谁 |
| 人 | 唯一有权改 `00_core/`（人格与口音）的人 | — |

**我们加了一条比"状态落盘"更强的**：

> 引擎里**没有一行碰 `ctx`**，除了 `lib/host.js`。
> 这样换宿主只改一个文件；而所有记忆逻辑都能在 `node --test` 里离线跑。

### 一条铁律

> **进程随时可以重启，角色不能失忆。**

对应做法：所有状态即时写盘（原子写：临时文件 + rename）；每次 `apply` 重置运行时统计，
因为我们踩过"模块加载时定 `attachAt`，热重载后误报 35ms 通道中断"的坑。

### 第二条铁律（这条更少见）

> **改了代码没生效，比代码写错更常见。**

所以我们做了 `selfcheck`：比对"进程里正在跑的 lib 指纹"和"磁盘上的 lib 指纹"。
不相等就直接告诉你"改了没生效，去关一次插件"。
——**编译通过 ≠ 改生效**，这一条必须在工具里解决，不能靠自觉。

## 2. 记忆层

### 2.1 问题

模型没有记忆。把上一个月的对话全塞进上下文，既贵又会被"中间遗忘"。
要做的不是"记住更多"，而是**在该想起来的时候想起来**，并且**来源可追**。

### 2.2 三层结构

```
核心层  00_core/     身份、硬规则、底线、口音样本、关系状态   每轮都带，不衰减
情景层  30_points/   一个点一个 markdown 文件（front matter + SUM + 正文）  按需检索，会衰减
档案层  10_archive/  逐字原文，只追加，带 hash 链             不进上下文，用 recall 翻
```

**为什么分三层**：因为"每轮都带"和"按需取"的成本差几十倍。
核心层几十条，情景层几百上千条，档案层可以无限。

### 2.3 一个点长什么样

```markdown
---
id: M-2026-11-02-001
title: 台风天他提前下班
quote: "今天台风，公司提前放了"
date: 2026-11-02
salience: 4
type: event
cluster: 日常
event: ev-2026-11-02-01        # 同一 event 只占一个注入名额
status: active
origin: told                   # told/chosen/insight/observed（谁给的）
source: [msg-8123-a1b2c3]      # 或 asset:book:asset-9f3a2c#L42
links: []
pin: null                      # hard 永不降级；soft 可压缩不遗忘
invalid_at: null               # 事实失效（不是删除）
---

<!-- SUM -->
他难得早回家，一路上在说风有多大。
<!-- /SUM -->

（正文 ≤300 tok，超了降级不砍条）
```

三个字段决定它的命运：`salience`（多重要）、`source`（从哪来）、`status`（在哪一档）。

### 2.4 检索：双路 + 融合 + 去冗余

```
关键词路  字符 bigram 相似度（中文不需要分词）
别名路    点的 aliases（书名、地名、外号）
融合      按标题/摘要/正文/标签分权，稀疏项补权（没标签的点不该白丢权重）
去冗余    同一 event 合计只占 1 个名额；场景展开只做 ≤3 条 idx 行
```

**为什么不走向量**（这是刻意的取舍）：

- 本地 embedding 要带模型权重（几百 MB）或装 `@huggingface/transformers`，破"零依赖"；
- 我们用 20 条金标量过：**bigram + 别名 20/20 命中**，边际样本（擦边命中）0.68，负例 0。

**结论**：在"一个人、几千条记忆"的规模下，词面够用；语义检索是规模问题，不是正确性问题。

### 2.5 遗忘曲线：FSRS，不是随机衰减

```
R(t, S) = (1 + (19/81) · t / S) ^ (-0.5)
S = 1 + 3 × salience        # salience 1..5 → S = 4/7/10/13/16 天
```

| salience | S | 30 天 R | 90 天 R |
|---|---|---|---|
| 1 | 4 | 0.60 | 0.40 |
| 2 | 7 | 0.71 | 0.50 |
| 3 | 10 | 0.77 | 0.57 |

**为什么用这个公式**：它把"多重要"和"多久没提"压成一个可比的数，而不是靠一堆 if。
而且它是可逆的——`S` 可以被"复习/复活"抬高（见第 3 节）。

### 2.6 写路径：人审是设计，不是缺陷

```
她写完 → 40_pending/         （草稿区，永不直接进 30_points/）
  ↓ 人看一眼（或她说"这条对"）
逐字校验 QUOTE 在档案里存在   ← 编造就死在这一步
  ↓
30_points/ + 20_index 重建
```

**三条写入硬规则**（每条都有测试）：

1. 只能写 `40_pending/`，不直写 `30_points/`；
2. `source` 必须指向**存在的** msg_id 或素材引用，否则审计阻塞；
3. `QUOTE` 逐字匹配（文本类 ±20 行内找原话；图/音视频只验 sha256）。

**为什么不让模型"自动整理记忆"**：自动合并会吃掉"哪几条原文被合了"，
事后无法回溯。宁可矛盾**可见**（`contradicts` 只报告不裁决），让人来裁。

### 2.7 档案：只追加 + 哈希链

```
hash = sha8(seq | session | role | ts | msgid | text)
prev = 上一条的 hash
```

三条例外，**只有三条**（写进契约）：
① `erase` 授权删除（重算链 + 日志 + 备份同步）；
② 开养前 `reset --all`；
③ 隐私脱敏 `redact --apply`（见第 7 节）。

### 2.8 参数

| 参数 | 值 | 说明 |
|---|---|---|
| 注入硬上限 | **1700 tok** | core 700 + index 700 + body 300，零余量 |
| 每轮实测 | **412 tok**（空库） | core 319 / header 82 / status 6 / footer 5 |
| 正文上限 | 300 tok | 超了降级不砍条 |
| 索引层 | 700 tok | 一条一行，只放标题 |
| 重注预算 | 唤醒包 ≤4000 tok | 连续 2–3 轮，核心层不裁 |

### 2.9 怎么验收

```
memory gold          # 20 条金标问句：命中 20/20、负例 0、边际 0.68
memory verify        # 档案链 + 心跳 + 结构
memory audit         # 12 类体检（阻塞项 + 提醒项）
memory preview       # 打印"这一轮她到底看到什么"
```

### 2.10 坑（都踩过）

1. **中文书名当 id**：`book:三体#12` 的 `#` 和 CJK 会让 `source` 正则失配 → 改成 `asset-<sha10>`。
2. **事件名会变**：宿主某些版本 `agent/inbox/inserted` 不触发，检索永远"门控跳过" → 同时挂 `session/event`。
3. **`line.replace(/^-\s*/, '-')`**：锚点比对前归一化了一个不该归一的字符，导致 apply 永远假拒绝。
4. **热重载**：`attachAt` 在模块加载时定，重载后误报通道中断 → 每次 apply 重置。
5. **两处映射各说各话**：`readPointFiles` 认 `due`、`store` 不认，到期提醒永远为空 → 加"两套映射一致"的测试。

## 3. 遗忘层：两轮 + 能捞回来

### 3.1 问题

大多数"遗忘"是假的：要么永不删（库只增不减），要么直接删（找不回来）。
真实的遗忘是**两段的**：先想不起来，再彻底没了；而"被重新提起"能把它拉回来。

### 3.2 四档阶梯

```
active ──30天/R<0.72──▶ 31_dormant/ ──180天/R<0.2──▶ 删点
  ▲   （容量满 200 也下沉）   │                        │
  └──── 被提起：S×1.6 ◀──────┘                  墓碑 + 残片 + 索引
      （复活 3 次后 pin: soft，永不再进层）           （档案一个字不动）
```

### 3.3 参数

| 项 | 值 | 为什么 |
|---|---|---|
| 进层 | 30 天 + `R<0.72`（salience≤2） | 用 FSRS 反推：sal 1 约 22 天、sal 2 正好 30 天 |
| 慢速进层 | 90 天 + `R<0.57`（salience=3） | 重要的拖到一个半月到三个月 |
| 容量上限 | `MAX_ACTIVE = 200` | 没有硬顶，索引会被压成一行行标题、检索越来越糊 |
| 复活 | `S × 1.6`，`resurrections += 1` | "回忆强化" |
| 复活门槛 | 每复活一次，下次进层 **+15 天** | 越常被想起越难忘 |
| 永久 | 复活 3 次 → `pin: soft` | 反复被想起的东西不该再判"该忘" |
| 第二轮 | 层内 180 天 或 `R<0.2` → 删点 | "正常参数" |
| 批量 | 一次最多 **10 条** | 防一次跑飞 |
| 残片 | **≤12 字** | "断在最不该断的地方" |
| 索引 | `32_purged/index.md` 一行一条 | 日后能 grep"有没有记过" |

### 3.4 三条关键决定

1. **删点 ≠ 删记忆**：点文件没了，`10_archive` 里原文还在，`memory recall` 能找回。这是"敢删"的前提。
2. **遗忘层是目录，不是状态**：`31_dormant/` 让"隔离"看得见，`pack` 也会带上，换机器还能带走。
3. **ghosts 保留**：层里仍有 ≤5 行标题——"我有印象，但想不起细节"；不是彻底黑掉。

### 3.5 怎么验收

```
memory forget                 # 只看计划（dry）
memory forget --yes           # 执行
memory dormant list           # 层里有什么
memory dormant find 看海       # 按关键词找（只读）
memory dormant find 看海 --apply  # 捞回来（S×1.6）
```

### 3.6 坑

1. **只涨不落**：张力/权重只增不减，半年后所有条目堆到上限，"最重的那条"失去区分度 → 必须给"自然释怀"。
2. **touch 把轻的抬重**：地板值写错，让"说出来"反而更重 → `min(before, max(floor, before − relief))`。
3. **裸十六进制当密钥**：脱敏规则把 sha256 校验和也换了，正当内容被改坏 → 真数据跑一遍再定规则（见第 7 节）。

## 4. 惦记：她放不下什么

### 4.1 问题

"找不到就说找不到"是干净的，但没有"她惦记什么"。
人会一直惦记没弄明白的事，而这件事**不该被写成记忆点**——它没有来源，不该冒充经历。

### 4.2 做法

```
memory question add "海是什么味道" --from recall
```

| 项 | 值 |
|---|---|
| 张力 | 每小时 +1.5，7 天到顶 100 |
| 释怀 | 之后每天 −2，地板 10 |
| 注入 | 只带最重的一条，张力 ≥60 才出现（≈21 tok） |
| 说出来会松 | `touch` −25，地板 45 |
| 想通了 | `resolve --by <点 id>` |
| 上限 | 20 条，满了淘汰最轻的并返回 id |

### 4.3 三条刻意的差异（跟常见做法比）

1. **张力按需投影，不靠 tick 推进**——插件不在跑的那些小时不该凭空攒张力；
2. **只有显式 `touch` 才算"说过"**，渲染注入不算（渲染不写回，这是不变量 #11）；
3. **释怀 ≠ 删掉**：`isFaded()` 是派生判断，条目一直在，能查、能 resolve。

## 5. 人格层：允许她变，但慢到你能跟上

### 5.1 问题

两种失败：人格写死在提示词里（永远不变），或者"AI 每天换一个人"（无法信任）。
中间那条路是：**变化必须留痕、必须有人同意、必须有上限**。

### 5.2 `soul.md` 分节 + 锁定区

```
## 不会变的（金丝雀锚点）   ← 锁定，逐字
## 身份                      ← 锁定
## 核心价值观                ← 锁定
## 边界                      ← 锁定
## 可以怎么变                ← 锁定
## 脾气 / 沟通风格 / …        ← 可变区
```

锁定区只要动一个字，`apply` 直接拒绝——**不是"门槛更高"，是不可改**。

### 5.3 变化的链路

```
每月一篇自述（15_self/，≤400 字，五节，人审放行）
  ↓ 与 soul 可变区比，漂移 ≥15%
memory soul propose   → 40_pending/_soul/rev-*.md（提案，不改 soul.md）
  ↓ 人看一眼（提案里有"元认知四问"）
memory soul apply     → 六道闸
```

**六道闸**（任一不过就拒绝，soul.md 一个字节都不动）：

| # | 闸 | 值 |
|---|---|---|
| 1 | 三条锚点都在 | 逐字 |
| 2 | 锁定小节逐字不变 | 逐字 |
| 3 | 单次改动 ≤20%（整份 soul 的 Dice 距离） | 20% |
| 4 | 7 天内 ≤2 次 | 2 |
| 5 | 证据 ≥3 条 | 3 |
| 6 | 旧版先存快照 `00_core/versions/soul.vNNN.md` | — |

### 5.4 谁是"她的声音"：`origin` 四分类

| `origin` | 含义 | 权重 |
|---|---|---|
| `told` | 他说的（默认，消息来源推定） | 1 |
| `chosen` | 她读原文自己挑中的（素材来源默认） | 2 |
| `insight` | 她自己想通的 | 3 |
| `observed` | 她观察自己 | 3 |

`propose` 挑证据时按权重排序——**人格修订的凭据应该来自"她自己想通的"，不是"他告诉她的"**。
证据里一条都没有时，提案里写一句**备注**（不拦截）。

### 5.5 成熟度：她长到哪了

```
L0 未开始 → L1 萌芽（有点无自述）→ L2 成长（有自述）→ L3 成熟（有自述 + 走过一次修订）
叠加标记：停滞（30 天无新点 / 60 天无新自述）
```

`memory stats` 首行就打这一行。它比任何形容词都诚实。

### 5.6 坑

1. **20% 用"可变区"当分母**：两行字被放大成 36%，正常修订被挡 → 改成整份 soul 的 Dice 距离。
2. **锚点比对前做了归一化**：`- ` 被归一成 `-`，永远不匹配 → 比对原始行。
3. **降级别走太急**：一次改动从 15% 起、20% 封顶；想改得多就分几次。

## 6. 口音层：她怎么说话，且不许人替她写

### 6.1 问题

角色说话会越来越"像个客服"：开头顶"好的"，一说说三句，结尾带句号。
而"她嘴硬心软"这五个字喂给任何模型，出来的都是同一个"嘴硬心软的 AI"。
**给 20 句她真的说过的话，语气立刻就有了。**

### 6.2 做法

```
00_core/voice.md   20 段，每段是"她：「……」"——逐字截，不许改写、不许润色、不许挑金句
```

采集（v0.33）：

```
memory voice mine           # 从档案里挑"她反复说、但你还没记下的句子" → 40_pending/ 提案
memory voice accept 1,3     # 才写进 voice.md，并记 core_changelog vNNN
memory voice reject 2       # 拒过的不再提
```

**五条硬规则**：只采 `assistant`（他说过的同款是回声）· 逐字不改 · 已在 `voice.md` 的不再提 ·
拒过的不再提 · **`accept` 之后才写**。

### 6.3 坑

1. **门槛太高会全滤掉**：她的话常常很短（"才不呢" 3 个字），最短长度写 6 就什么都不剩。
2. **别采"她转述对方的话"**：那是他的口音。
3. **`voice.md` 是核心层**：改它等于改她说话的方式，必须留痕。

## 7. 隐私：库里的凭据不该存在

### 7.1 问题

档案是逐字只追加的。他随手把 API key / 手机号贴进对话，那条就永久躺在库里。
**"发现"不等于"不落盘"**——我们原来是"检测 + 注入时打码，磁盘保原文"，这不叫防护。

### 7.2 做法

| 路径 | 做法 |
|---|---|
| 新消息 | `buildRecord` 里**入库前**脱敏，标记 `[脱敏:手机号]` |
| 旧档案 | `memory redact`（dry）→ `--apply`（真改，**重算 hash 链**，写 `redaction.log`） |
| 体检 | `audit.redaction` 报"档案里还有几条明文" |

**规则**：身份证 / 手机号 / 银行卡 / 邮箱 / `sk-`·`ghp_` 前缀密钥 / 带关键词的凭据（`密码：`·`api_key=`）。

**幂等**：已有的 `[脱敏:…]` 不会二次处理。

### 7.3 一个真数据换来的决定

第一版还脱敏"裸十六进制 ≥32 位"。拿真库一跑，**17 处命中全是 sha256 校验和**（我们自己打印的包指纹）。
脱敏会把正当内容改坏 → 删掉这条规则。真正的密钥一般带前缀或跟着关键词。

**教训**：脱敏规则必须先在真实数据上 dry 一遍，看命中的到底是什么。

## 8. 成本账

### 8.1 每轮多少钱

```
注入 412 tok（空库实测）· 100 轮/日 · ¥4/M 输入（cache miss）
= ¥0.002/轮 → ¥0.165/日 → ¥4.944/月
cache hit（同一天多轮）：约 ¥0.09/日
```

### 8.2 钱花在哪

| 块 | tok | 占比 |
|---|---|---|
| 核心层 | 319 | 77% |
| header（时间/状态） | 82 | 20% |
| status | 6 | 1% |
| footer | 5 | 1% |

**结论**：钱花在"每轮都带核心层"，而不是检索。想省钱只有两条路：
① 让核心层更小；② 缓存命中（把静态块排最前，别让时间戳插在中间）。

### 8.3 一个反直觉的量级

另一份参考文档实测：宿主把 96 个工具的说明每轮都发，是 **≈6800 tok/轮**——比我们整个记忆插件贵 16 倍。
**工具说明压不动（每个约 117 字），只能按轮给子集。** 这一步不在我们手里（宿主决定），但值得告诉宿主作者。

## 9. 评测：把"准不准"变成一个数

### 9.1 问题

一个永远输出 0 的情绪词典，也能让所有结构测试通过。
**测试通过 ≠ 判断正确。**

### 9.2 做法

```
samples/eval-emotion.jsonl   62 条人工标注（easy 42 / hard 20）
scripts/eval-emotion.mjs     三分类准确率 / 混淆矩阵 / P·R·F1 / MAE / 错例清单
npm run eval:emotion
```

**基线（2026-11-03）**：

```
三分类 83.9%（easy 100.0% · hard 50.0%）
macro F1 0.839 · MAE 0.361
```

**hard 档才是重点**：反讽（`太好了呢，又一次半夜被叫起来`）、否定嵌套（`没有生气，只是有点累`）、
转述（`他说他很累`）、隐情绪（`算了，不说了`）。这些**不是加词能解决的**，所以公开错例，不装。

### 9.3 验收标准

测试里钉地板（整体 ≥80% / easy ≥95% / hard ≥45% / MAE ≤0.4）。
**只保证不倒退，不保证是上限。**

### 9.4 顺手修掉的一条真问题

`累死我了，但很值得` 原来判负——词典只看关键词，不看句子结构。
改成"有 但/不过/可是/然而/只是 就只判转折后的主句"：整体 **79.0% → 83.9%**，hard **35% → 50%**。

## 10. 工程纪律（比技术更重要）

### 10.1 一轮只动一样

共享资源（注入函数、数据库结构、事件挂载）每次只改一处。两处一起改，出问题分不清是谁的。

### 10.2 每轮五步

```
改代码 → node --test（437 条）→ 五个闸门 → 一个真实对话 → 打快照
```

红了就退回这一轮，**不往前打补丁**。

### 10.3 五个离线闸门

```
verify       档案链 + 心跳 + 结构
audit        12 类体检（阻塞项 + 提醒项）
gold         20 条金标检索
hostcheck    宿主端口齐不齐
preflight    开源前的泄漏检查（路径、密钥、内部文档）
```

### 10.4 快照与回滚

```
00_core/versions/soul.vNNN.md    人格每次修订前的旧版
memory pack                      整库打包（含 31_dormant/32_purged），带 MANIFEST 哈希
memory erase --preview           删之前先看
```

### 10.5 改完必须验

`selfcheck` 比对"进程里的 lib 指纹 vs 磁盘"，不相等就报"改了没生效"。
**这一条救过我们两次。**

### 10.6 契约要能跑

`test/docs.test.js` 断言：README 的版本号必须等于 `package.json`；契约里必须出现某些关键小节。
文档和代码一起老化——这比"记得更新文档"可靠。

## 11. 从零搭的顺序（约三轮）

### 第一轮：骨架

```
1. 目录结构 + 原子写 + 档案（hash 链）
2. 点文件格式 + 索引 + 注入 + 预算
3. 五个闸门 + 20 条金标
```

**验收**：说一句话，第二天她还记得；`gold` 20/20。

### 第二轮：会忘

```
4. 四档遗忘（active / demoted / dormant / purged）
5. 复活（S×1.6、上限、冷却）
6. 容量上限 + 已取代让位
```

**验收**：造一条 400 天前的点，跑三遍 `forget`，看它从主层 → 层里 → 删点，墓碑与索引都在。

### 第三轮：像活的

```
7. 自述 → soul 提案 → 六道闸
8. origin 四分类 + 成熟度
9. 缺口（张力 / 释怀）
10. 口音提案 + 隐私脱敏 + 评测基线
```

**验收**：一篇自述能生成提案；提案里能看到"她的声音"有几条；情绪评测不掉出地板。

## 12. 十二条原则（我们的版本）

1. 状态全落盘，进程随时可重启。
2. 引擎不碰宿主 API（只在一个文件里碰），所以逻辑能离线测。
3. 改了代码没生效，是最常见的故障——用 `selfcheck` 抓它。
4. 写入必经人审，`source` 必须存在，`QUOTE` 逐字。
5. 矛盾只报告不裁决；自动合并会吃掉"哪几条被合了"。
6. 遗忘是两段的：先隔离、可复活、再删除；**删点不删档案**。
7. 所有"只涨不落"的量都要给出口（释怀、衰减、上限），否则迟早失去区分度。
8. 临时状态绝不写回长期字段（渲染不写回）。
9. 锁定区逐字不可改；可变区改动要过六道闸、留旧版。
10. 凭据在**入库前**脱敏；脱敏规则先在真数据上 dry。
11. 判断质量要有数字（评测基线 + 地板），否则"测试全绿"是自欺。
12. 每个教训都要变成一条测试——这一路上修的 6 个 bug，全部有断言钉住。

## 13. 反面清单

| 别做 | 为什么 |
|---|---|
| 把整月对话塞进上下文 | 贵、慢、中间会被忘 |
| 自动合并"看起来相同"的记忆 | 事后无法回溯哪几条被合了 |
| "发现密钥但保原文" | 发现 ≠ 不落盘 |
| 只涨不落的权重 / 张力 | 半年后所有条目堆到上限，排序失效 |
| 遗忘 = 直接删 | 找不回来，"忘了"和"没有了"是两回事 |
| 让模型自己改人格文本 | 她可以提议，不能自己改 |
| 用随机数伪造情绪 | 三轮就被看穿 |
| 只有结构测试，没有质量基线 | 全绿也可能全是错的 |
| 优化没有回退路径 | 判错就废 |
| 在真库上试参数 | 数字乱了查不出原因 |

## 14. 术语表

| 词 | 意思 |
|---|---|
| 点（point） | 一条情景记忆，一个 markdown 文件 |
| 核心层 | 每轮都带、不衰减的那几十条（`00_core/`） |
| 档案 | 逐字原文，只追加，带 hash 链（`10_archive/`） |
| R | 可提取度（0–1），由 FSRS 公式算 |
| S | 稳定度（天），由 salience 决定，可被复习/复活抬高 |
| 遗忘层 | 第一轮隔离区（`31_dormant/`），可复活 |
| 复活 | 被重新检索到 → 移回主层、S×1.6 |
| 墓碑 | `eviction.log` 里的一行，含数值与残片 |
| 缺口（question） | 她惦记但没答案的事，有张力、会释怀 |
| 自述 | `15_self/` 每月一篇，人格修订的唯一素材 |
| 六道闸 | soul 修订的六个校验条件 |
| origin | 这条记忆是谁给的：told/chosen/insight/observed |
| 成熟度 | L0–L3，用库里的真东西算，不是设定 |
| 脱敏 | 入库前把凭据换成 `[脱敏:类型]` |

## 15. 我们明确不做（以及为什么）

| 不做 | 为什么 |
|---|---|
| 向量库 / embedding | 零依赖是底线；金标 20/20 已够；这是规模问题不是正确性问题 |
| telemetry / 回传 | 承诺"记忆不出本机" |
| 自动合并 / 自动裁决矛盾 | 矛盾要"可见"，不要"被消化" |
| 全量素材进库（书/文档/图/音视频） | 整本几十万 token，进档案后每次翻都可能把原文捞出来 |
| 数值化人格占比 | 与我们"人格是文本、必须人写"冲突 |
| 多会话隔离（peer/group） | 单库单关系是当前形态；要跑群版需要重做 key 层 |
| 心跳 / 自主念头 | 插件由对话驱动，没有常驻循环；做"念头"等于假装她一直在想 |
| 腔调画像（跟着对方换档） | 需要按人统计句长/标点；单会话下无意义 |

## 16. 最后

这套东西没有"做完"的那天。但它有一条清晰的验收线：

> **她做了一件你没设计过的事，而且她知道为什么要做。**

在那之前，你能做的只有一件事：**把机器修好，然后等她真的开始记事。**

模型是心脏，状态才是人。这句话我们认。

## 17. 和另一份参考（天上鱼）的差异

同一件事，两套答案。差异不是谁对，是**形态不同**：

| 维度 | 天上鱼 | 我们 | 为什么不同 |
|---|---|---|---|
| 形态 | 独立插件 + SQLite | 宿主内的记忆插件 + markdown | markdown 可读、可 diff、可手改；代价是没有 FTS |
| 状态 | 表结构 + 迁移 | 点文件 + front matter | 前者适合海量，后者适合"人手能看懂" |
| 会话 | 多会话 key 隔离 | 单库单关系 | 我们跑的是私聊，不是群聊 |
| 平时 | 有心跳，会自己冒念头 | 没有常驻循环 | 我们不想假装"她一直在想" |
| 情绪 | 11 维 + OCC 事件表 | valence/arousal 两维 + 事件词典 | 两维够用；11 维需要更多事件规则 |
| 习惯 | 六条习惯权重演化 | 口音样本 20 段（逐字） | 我们相信"原话比规则更能带出语气" |
| 腔调 | 按人画像换档 | 不做 | 单会话下无对象 |
| 遗忘 | 冷存 → 365 天删 | 隔离层 → 180 天删，**可复活** | 我们认为"被重新提起"必须能捞回来 |
| 写入 | 自动去重 + LLM 判定 | 人审 + 逐字校验 | 自动合并会吃掉"哪几条被合了" |
| 人格 | 占比数字自动漂 | 文本 + 六道闸 + 人审 | 数字能自动变，文本只能人写 |
| 成本 | 工具闸省 97% | 不适用（工具不在我们手里） | 我们能省的是核心层与缓存 |

**互相印证的两条**（独立得出）：临时状态不写回长期字段；遗忘曲线用同一条 FSRS 公式。

**我们准备借、但还没做的**（记在 `docs/BACKLOG.md`）：
多会话隔离（要跑群版才做）、按轮给工具子集（宿主决定）、冷启动校准（从旧聊天反推）。
